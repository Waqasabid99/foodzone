# FoodZone API v1

One backend serves both clients. The website and the React Native app call the
**same endpoints** with the same request and response shapes — the only
difference is how they carry the session (see [Auth](#auth)).

Base URL: `/api/v1` (mobile: `https://<your-domain>/api/v1`)

## Interactive reference

This file is the narrative — why an endpoint exists, how a flow fits together,
what the state machines allow. The **exact** request shapes live in an OpenAPI
3.1 document generated from the code:

| | |
| --- | --- |
| Swagger UI | `/api/docs` |
| The document | `/api/docs/openapi.json` |
| Committed copy | `src/generated/openapi.json` |

Both are served outside production; in production they require
`API_DOCS_ENABLED=true`, because the document enumerates every endpoint and
permission key. Endpoints enforce their own authorisation regardless.

The document is generated by reading the options each route hands to
`apiHandler` — the same options the pipeline enforces — so parameters, bodies,
permissions, branch scoping and rate limits cannot drift from the server. Run
`npm run docs:api` after changing any route or schema and commit the result;
`npm run docs:api:check` fails in CI if the committed copy is stale.

Response *payloads* are the exception: their shape comes from Prisma `select`
clauses in the service layer, and there is no schema object to read back, so
successful responses are documented as the envelope with a free-form `data`. A
route can publish a real one by adding `doc: { response: someZodSchema }` to its
options. Prose in this file remains the source for what those payloads contain.

## Response envelope

Every response — success or failure, including unhandled server errors — is JSON
in one of these two shapes. A client can parse without ever branching on content
type.

```jsonc
// success
{ "success": true, "data": { }, "meta": { } }   // meta only on paginated lists

// failure
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": { } } }
```

Branch on `error.code`, never on `message` (messages are user-facing and may be
reworded):

| Code | HTTP | Meaning |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Bad input. `details` maps field → messages. |
| `UNAUTHORIZED` | 401 | Missing/expired token — refresh, then retry. |
| `FORBIDDEN` | 403 | Authenticated but not allowed. |
| `NOT_FOUND` | 404 | No such resource (or not yours). |
| `METHOD_NOT_ALLOWED` | 405 | Wrong HTTP verb for this path. |
| `CONFLICT` | 409 | Valid but not permitted now (duplicate email, unavailable item). |
| `PAYLOAD_TOO_LARGE` | 413 | Body exceeded the endpoint's limit (1 MB by default). |
| `RATE_LIMITED` | 429 | Quota spent. Wait `Retry-After` seconds, then retry. |
| `INTERNAL_ERROR` | 500 | Server fault. Safe to retry once. `details.requestId` identifies it in the logs. |
| `SERVICE_UNAVAILABLE` | 503 | Database or a dependency is down. Retry with backoff. |

`FORBIDDEN` from a permission check carries `details.required` — the permission
keys the endpoint needed — which is what makes a 403 debuggable.

### Rate limiting

Every response carries `RateLimit-Limit`, `RateLimit-Remaining` and
`RateLimit-Reset` (seconds until the window rolls over). Back off when
`RateLimit-Remaining` reaches 0 rather than waiting for the 429. A `RATE_LIMITED`
response also carries `Retry-After`.

### Request tracing

Every response carries `x-request-id`. Send your own `x-request-id` on a request
and it is echoed back and used in the server logs, which is how a client-side
bug report gets tied to a server-side log line.

## Auth

Two transports, one implementation:

- **Mobile** — read `accessToken` / `refreshToken` from the login response, store
  them (Keychain / EncryptedSharedPreferences, **not** AsyncStorage), and send
  `Authorization: Bearer <accessToken>`.
- **Web** — the same endpoints also set `fz_access` / `fz_refresh` httpOnly
  cookies, so the browser needs no token handling.

The `Authorization` header takes precedence over cookies.

Access tokens last **15 minutes**; refresh tokens last **30 days** and are
**rotated on every use** — each refresh returns a new refresh token and revokes
the old one. Store the new one immediately; replaying a used token fails.

Send `"client": "ios" | "android" | "web"` on auth calls so sessions are
attributable per device.

A session payload:

```json
{
  "user": {
    "id": "...", "name": "...", "email": "...", "phone": null,
    "status": "ACTIVE", "emailVerified": true, "isSuperAdmin": false,
    "roles": [{ "key": "customer", "name": "Customer", "branchId": null }],
    "permissions": ["self.place_order", "self.view_own_orders"]
  },
  "accessToken": "eyJ...",
  "refreshToken": "9f3...",
  "expiresIn": 900,
  "tokenType": "Bearer"
}
```

`permissions` is the caller's **effective** permission set — role grants, minus
denials, plus per-user overrides. Render UI from it, but never trust it for
access control: every endpoint re-checks server-side. A super admin receives
`["*"]`.

### Verification and account state

Registration returns a session immediately with `status: "PENDING_VERIFICATION"`
and `emailVerificationRequired: true`. The account can browse and build a cart;
actions that need a reachable address are refused with `FORBIDDEN` and
`details.reason: "EMAIL_NOT_VERIFIED"` until `/auth/email/verify` succeeds.

Codes are six digits, valid for 15 minutes, single-use, capped at 5 attempts,
and issuing a new one retires the previous one. Requesting a resend inside the
60-second cooldown returns `RATE_LIMITED` with `Retry-After`.

`SUSPENDED` and `DEACTIVATED` accounts are refused at login with `FORBIDDEN` and
`details.reason` of `ACCOUNT_SUSPENDED` / `ACCOUNT_DEACTIVATED`.

### Session invalidation

Changing a password, resetting one, suspending an account or detecting refresh
token reuse revokes **every** refresh token and moves `tokensValidFrom` forward,
which kills access tokens already in flight rather than waiting out their TTL.
A password *change* then hands the calling device a fresh session, so the person
who changed it stays signed in where they did it.

Replaying an already-rotated refresh token is treated as theft: the entire token
family is revoked and every device must log in again.

**Staff never receive a password from an administrator.** `POST /admin/users`
creates the account with no password and emails a single-use invitation code;
the invitee sets their own password at `/auth/invitations/accept`, which also
verifies their email and activates the account.

**Permissions are seeded, not authored.** There is no endpoint that creates one.
Administrators compose the 292 seeded keys into roles.

**System roles are immutable** — the 20 seeded roles cannot be renamed, edited,
re-permissioned or deleted, because the seed would overwrite the change on the
next deploy. Create a new role instead.

Two escalation guards apply to every role write, and a super admin bypasses both:

- you cannot grant a permission you do not hold yourself
- you cannot create or grant a role at or above your own `level` (lower is more
  senior)

Branch-scoped roles must name a `branchId` unless the actor is a super admin,
and the actor must already have reach into that branch. Suspending, deleting or
re-permissioning a user takes effect on their live sessions immediately.

### Opening hours

Hours are **minutes from midnight in the branch's own timezone**, and a closing
time may exceed 1440 to express service past midnight — 20:00–02:00 is
`{ opensAt: 1200, closesAt: 1560 }`. Several rows per weekday give split shifts.
A row may name a `channel` to apply only to that channel; a row with no channel
applies to all of them.

Every branch payload carries `openState`:

```json
{ "isOpen": false, "reason": "OUTSIDE_HOURS", "nextOpenAt": "2026-09-10T05:00:00.000Z" }
```

`reason` is one of `OPEN`, `OUTSIDE_HOURS`, `CLOSURE` (with `closureReason`),
`NO_HOURS_SET` or `INACTIVE`. Minutes rather than timestamps means a daylight
saving change never silently shifts opening times by an hour.

## Settings

| Method | Path | Auth | Notes |
| --- | --- | --- | --- |
| `GET` | `/settings/public` | – | `?branchId=` — public settings only |
| `GET` | `/admin/settings` | `settings.read` | Registry, values and the source of each |
| `PUT` | `/admin/settings` | `settings.update` | `{ branchId?, values: { key: value } }` |
| `DELETE` | `/admin/settings/{key}` | `settings.update` | `?branchId=` — removes one override |

Settings are **defined in code** (`src/server/settings/registry.js`), stored in
the database, and resolved in three layers:

    branch row  →  global row  →  registry default

So a branch stores only what it overrides, and adding a setting in code has a
correct value everywhere without a migration. Each entry declares a type and a
schema, so a delivery fee can never be saved as `"free"`, and an `isPublic` flag
that is the sole gate on `/settings/public` — a new setting is private unless
someone marks it otherwise. Only entries flagged `branchOverridable` accept a
branch-level value.

## Media & uploads

| Method | Path | Auth | Notes |
| --- | --- | --- | --- |
| `POST` | `/media/uploads` | `media.upload` | `{ mimeType, sizeBytes, ownerType?, ownerId? }` → ticket + target |
| `POST` | `/media/uploads/confirm` | `media.upload` | `{ ticket }` → the recorded asset |
| `GET` | `/media` | `media.upload` | `?ownerType=&ownerId=&mimeType=` |
| `GET`/`PATCH` | `/media/{id}` | `media.upload` | PATCH attaches the file to a record |
| `DELETE` | `/media/{id}` | uploader, or `media.delete` | Removes the object, then the row |
| `PUT` | `/media/local/{ticket}` | ticket | Local driver only — the ticket is the authorisation |
| `GET` | `/media/file/{key}` | – | Local driver only — serves the file |

Uploads are **direct to the provider**, in three steps:

1. `POST /media/uploads` returns an `upload` target — `method`, `url`, and
   either `fields` (multipart POST, Cloudinary) or `headers` (PUT, S3/R2) — plus
   a `ticket` and the `policy.compression` the client must apply first.
2. The client uploads the bytes straight to the provider. They never pass
   through our server, which is what makes 100MB videos and serverless
   deployment possible at all.
3. `POST /media/uploads/confirm` verifies the object landed, reads its **real**
   size back from the provider, and writes the `MediaAsset` row. Confirming
   twice returns the same asset.

**Compression.** Because the bytes bypass our server, compression happens at the
client, following `policy.compression` (images: longest edge 2000px at ~0.82
quality; video: H.264 mp4, 1280px, ~2.5 Mbps). Cloudinary additionally applies
an incoming transformation (`q_auto:good`), so what it stores is already
re-encoded. Neither is trusted: confirm rejects anything over the ceiling and
deletes it, so a client that skips compression simply fails.

**Storage driver** is `STORAGE_DRIVER`: `cloudinary`, `s3` (also Cloudflare R2,
Backblaze, MinIO — set `S3_ENDPOINT`) or `local`. The API response shape is
identical across all three, so switching provider is an env change plus a
migration of existing objects. `local` requires a persistent filesystem and must
never be used on serverless.

Storage keys are random and date-partitioned (`branch/2026/09/<32 hex>.webp`), so
one customer's receipt URL cannot be guessed from another's.

## Background jobs

| Method | Path | Auth |
| --- | --- | --- |
| `GET`/`POST` | `/api/internal/jobs/outbox` | `Authorization: Bearer $CRON_SECRET` |
| `GET`/`POST` | `/api/internal/jobs/maintenance` | `Authorization: Bearer $CRON_SECRET` |
| `GET`/`POST` | `/api/internal/jobs/attendance` | `Authorization: Bearer $CRON_SECRET` |

Side effects are written to an outbox table **inside the transaction that caused
them**, so a notification cannot be lost when the process dies after the commit.
A worker drains it with retries and exponential backoff; after
`OUTBOX_MAX_ATTEMPTS` an event is marked `FAILED` rather than retried forever.

Claiming uses `FOR UPDATE SKIP LOCKED`, and `availableAt` doubles as a lease, so
a crashed worker's rows become claimable again instead of sticking in
`PROCESSING`. Several workers — or an overlapping cron and in-process loop — can
run safely at once.

Two deployment shapes, same code:

- **Docker / VPS**: set `WORKER_IN_PROCESS=true`. `instrumentation.js` starts an
  interval loop once per server instance.
- **Vercel**: leave it false. `vercel.json` schedules the outbox endpoint every
  minute and maintenance nightly.

Without `CRON_SECRET` these endpoints return **404** in production rather than
running unauthenticated — an open job trigger is a free denial of service. In
development they run without it.

**Registered outbox handlers**: `notification.push`, `notification.push_bulk`,
`notification.email`, `order.placed`, `order.status_changed`, `order.cancelled`.
Order notifications run out of band on purpose — by the time one fires the
customer's order is already with the kitchen, so a slow mail server or an
expired push token must never be able to fail the order itself. Only the
transitions a customer cares about produce a notification; one per internal step
trains people to ignore all of them.

**The nightly maintenance job** prunes delivered outbox events, clears expired
timed 86s, prunes `QrScan` rows older than 180 days, and deletes carts past
their 7-day expiry.

**The nightly maintenance job also alerts on low stock**, to whoever holds
`purchase_orders.create` — the grant that can actually raise an order, because
telling people who cannot act turns an alert into noise they learn to dismiss.
"Low" means what the item list already means by it, at or below the reorder
level in some location, rather than a second definition nobody can reconcile
with the screen. Inactive items are left out, and a branch is only told again
when something has *newly* gone low: restocking raises no alarm, and the
message always lists everything low now, because that is what somebody raising
an order needs.

**The nightly attendance job** turns raw punches into the attendance days
payroll is built from. It runs per branch, because "yesterday" is a different
day in each branch's own zone, and it reaches three days back rather than one,
which heals a hole left by a night the worker missed. Re-folding a day
recomputes it from the same punches and writes the same answer; what keeps
that safe is that derivation refuses a day already paid and a day a human
corrected by hand. It is
separate from maintenance deliberately — an absence becomes a row only when
something derives the day, so a fold that quietly stopped would be discovered
on payday. Days already paid, and days a human corrected by hand, are left
alone.

## Catalog administration

Products are **global**; a branch decides what it sells by putting a product on
a menu. So catalog endpoints are not branch-scoped, and menu endpoints are.

### Categories

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/categories` | `categories.read` — `?tree=&search=&isActive=&parentId=&includeCounts=` |
| `POST` | `/admin/categories` | `categories.create` |

Categories nest up to **4 levels**. Two invariants are enforced on every write:
a category can never become its own ancestor, and the tree cannot exceed that
depth. A cycle would turn any recursive read into an infinite loop and is
introduced by a single careless drag, so it is rejected rather than repaired.

Deleting is refused while products or child categories still point at the
category — deactivate it to hide it instead.

### Products and variants

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/products` | `products.read` — `?search=&categoryId=&stationId=&type=&isActive=&isFeatured=&includeDeleted=` |
| `POST` | `/admin/products` | `products.create` |
| `GET` | `/admin/products/{id}` | `products.read` — `?includeDeleted=true` |
| `PATCH` | `/admin/products/{id}` | `products.update` |
| `DELETE` | `/admin/products/{id}` | `products.delete` — soft delete |
| `POST` | `/admin/products/{id}/restore` | `products.delete` |
| `PUT` | `/admin/products/{id}/publish` | `products.publish` — `{ isActive }` |
| `PUT` | `/admin/products/{id}/images` | `products.update` — replace-all gallery |
| `GET`/`POST` | `/admin/products/{id}/variants` | `variants.read` / `variants.create` |
| `PATCH`/`DELETE` | `/admin/products/{id}/variants/{variantId}` | `variants.update` / `variants.delete` |

**Every product has at least one active variant, and exactly one default.** A
"simple" product is not a special case in the data — it is a product with one
variant called `Regular`. Post `{ price: 250 }` and the service creates that
variant for you, with a generated SKU. This is why ordering, recipes, stock and
menu pricing only ever deal with variants and never branch on product type.

Adding a second variant promotes a `SIMPLE` product to `VARIANT` automatically,
so the storefront knows to render a size picker.

**A product is always created unpublished.** `products.publish` is a separate
permission, so accepting `isActive` on create would let anyone holding only
`products.create` put an unreviewed item in front of customers. Publish is its
own endpoint, and it refuses a product with no active variant.

Deleting is a **soft delete**: order history references products by id, and a
hard delete would cascade through variants and take order lines' pricing context
with it. The product is removed from every menu at the same time, so it cannot
be ordered while the row survives for reporting. Restoring brings it back
unpublished — it left every menu, so someone has to look at it first.

A variant that has been ordered cannot be deleted, and the last active variant
of a product can be neither deactivated nor deleted.

### Modifiers

| `GET`/`PATCH`/`DELETE` | `/admin/modifier-groups/{id}` | `modifiers.read` / `.update` / `.delete` |

| `GET` | `/admin/products/{id}/modifier-groups` | `products.read` |

Groups are **reusable**: "Extras" is authored once and attached to thirty
burgers. A product may tighten the rules for itself, so the effective rule is
always *the product's override, else the group's* — and the API returns that
merged value, so no client has to compute it.

Selection rules are validated on write, not only at checkout: a group asking for
3 choices out of 2 options is a trap that would otherwise surface only when a
customer cannot complete an order. `allowQuantity` relaxes this, since one
option taken three times satisfies a minimum of three. Marking a group required
forces its minimum to at least 1, so "required" and "minimum 0" can never
disagree.

### Combos

| Method | Path | Permission |
| --- | --- | --- |
| `GET`/`POST` | `/admin/products/{id}/combo-groups` | `combos.read` / `combos.create` |
| `PATCH`/`DELETE` | `/admin/products/{id}/combo-groups/{groupId}` | `combos.update` / `combos.delete` |
| `POST` | `/admin/products/{id}/combo-groups/{groupId}/options` | `combos.update` |
| `PATCH`/`DELETE` | `.../options/{optionId}` | `combos.update` |

A combo is a **product of type `COMBO`** whose price is its own variant's base
price plus each chosen option's `priceDelta`. Modelling it as a product means a
combo can sit on a menu, be discounted, be attributed to a creator video and
appear in reports without any of those systems learning a second concept.

An option without a `variantId` resolves to the product's default variant at
definition time, so a combo's price is knowable from its definition alone. A
combo may not contain itself or another combo — nesting makes pricing, stock
explosion and the "what did they actually eat" report unbounded.

### Menus

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/menus` | `menus.read` — `?branchId=&type=&isActive=` |
| `POST` | `/admin/menus` | `menus.create` |
| `GET`/`PATCH`/`DELETE` | `/admin/menus/{id}` | `menus.read` / `.update` / `.delete` |
| `GET`/`POST` | `/admin/menus/{id}/sections` | `menus.read` / `menus.update` |

| `GET` | `/admin/menus/{id}/items` | `menu_items.read` |

| `PATCH` | `/admin/menus/{id}/items/{itemId}` | `menu_items.update_price` |

Menus are branch-scoped. Sub-resource routes carry only a menu id, so they read
the menu's branch and then run the same branch-access check `apiHandler` applies
to `?branchId=` routes — a branch manager cannot reach another branch's menu.

**A menu item is always a (product, variant) pair.** `POST /items` without a
`variantId` adds one row per active variant, so a branch can price a large pizza
differently on delivery and 86 only the large one when the big trays run out. It
also makes the unique index real: Postgres treats NULLs in a unique index as
distinct, so a nullable `variantId` could not prevent duplicates.

Scheduling uses **minutes from midnight in the branch's timezone**, matching
opening hours, with an end past 1440 for a window running into tomorrow
(20:00–02:00 is `1200 → 1560`). Optional `daysOfWeek` and an `activeFrom`/
`activeTo` date range narrow it further. Only one menu per (branch, type) may
be `isDefault`.

Pricing splits by permission on purpose: `menu_items.update_price` reprices,
`menu_items.toggle_availability` runs the 86 switch. A shift manager can mark
items sold out all night without ever being able to change a price.

**The 86 switch.** `{ isAvailable: false }` turns an item off until someone
turns it back on; adding `until` makes it a timed 86 ("back tomorrow"). An
expired deadline reads as *available* immediately — a cron that has not run yet
must never keep an item hidden past its own deadline. The nightly maintenance
job clears expired rows as tidy-up, not as the mechanism.

### Cloning a menu

| | |
| --- | --- |
| `POST /api/v1/admin/menus/{id}/clone` | Copy a menu to another branch or channel |

Setting up a second branch, or a delivery menu priced above dine-in, otherwise
means re-entering every line by hand — which is also the point at which two
branches quietly stop selling the same thing. The body is entirely optional:

```json
{ "branchId": "...", "type": "DELIVERY", "name": "...", "slug": "...",
  "isActive": false, "isDefault": false, "includeItems": true }
```

`branchId` and `type` default to the source's own, so an empty body clones the
menu in place as `"<name> (copy)"`. Products and variants are global, so nothing
about the catalog is copied alongside — the clone points at the same sellable
units.

Three things are deliberately **not** copied:

- **Active state.** The clone is created inactive unless `isActive` is set. You
  clone in order to adjust prices *before* anyone can order from it; going live
  the instant it is created is the opposite of the point.
- **The 86 state.** `isAvailable` and `unavailableUntil` say that *this* branch
  ran out of something *today*. Carrying that across would mark items sold out
  that are sitting in the other branch's fridge.
- **`isDefault`.** Two defaults on one (branch, type) is a resolution
  ambiguity. Ask for it explicitly and it displaces the existing default, the
  same way creating a menu does.

Authorisation takes **two** branch checks: `menus.read` at the source and
`menus.create` at the target. Checking only the source would let someone clone
into a branch they have no business touching; checking only the target would let
them read a menu they cannot otherwise see by copying it to their own branch.

The response carries `clonedFrom`, `sectionCount` and `itemCount`.

### Bulk import and export

| | |
| --- | --- |
| `GET /api/v1/admin/catalog/export?resource=…` | Download CSV (`catalog.export`) |
| `POST /api/v1/admin/catalog/import` | Upload CSV (`catalog.import`) |
| `GET /api/v1/admin/catalog/format` | The columns each resource accepts |

Four resources: `categories`, `products`, `variants`, `menu-items`. A
`menu-items` export may be narrowed with `branchId` or `menuId`.

The export returns the file itself, not the JSON envelope — the caller is a
browser following a link. What it writes is exactly what the importer reads, so
**export → edit in a spreadsheet → import** is a round trip, and importing an
untouched export changes nothing.

That works because every row is identified by a **natural key** — a category's
slug, a product's slug, a variant's SKU, and for a menu item the combination of
branch code, menu slug, product slug and variant SKU. Database ids are
deliberately absent from the format: they mean nothing to the person editing the
file, and they invite an import run against the wrong environment.

Import takes the file as a JSON string, which keeps the endpoint identical for
the website and the mobile app:

```json
{ "resource": "products", "csv": "slug,name,…", "dryRun": true }
```

**Send `dryRun` first** for any file you did not generate five minutes earlier.
The response is identical apart from `applied`, so one screen can show what
would happen and then what did:

```json
{ "resource": "products", "dryRun": true, "applied": false,
  "rowsRead": 120, "rowsValid": 118, "created": 0, "updated": 0,
  "unknownColumns": ["notes_for_me"],
  "errors": [{ "line": 14, "errors": ["price: expected an amount, got \"free\""] }] }
```

Rules worth knowing before editing a file:

- **A blank cell leaves the existing value alone.** Clearing a field is
  explicit, with `--`. A spreadsheet round-trip blanks cells constantly; treating
  that as "wipe every description" would be a data-loss machine.
- **Nothing is ever deleted.** A row missing from the file means "not
  mentioned", never "remove it" — a dropped row must not be able to retire a
  product that is on a live menu. Deletion stays a deliberate act through the
  normal endpoints.
- **All or nothing.** Every row is validated before anything is written, and the
  writes are one transaction. A catalog half imported, with new prices on some
  products and old on others, is worse than an import that failed, because
  nobody can tell by looking which is which.
- **Every problem in a row is reported at once**, with the line number as the
  spreadsheet shows it (the header is line 1). One round of corrections, not
  fifty.
- Lists are pipe-separated: `VEG|HALAL`.
- Prices are read as exact decimal strings, never through a float. A currency
  symbol and thousands separators are stripped, because that is what a cell
  formatted as currency exports as.
- Two rows sharing a key is an error, not a silent last-wins.
- Imported products are **draft** unless `is_active` says otherwise, exactly
  like `POST /admin/products` — nothing reaches a menu because a spreadsheet
  mentioned it.
- A product whose slug belongs to a soft-deleted product is refused rather than
  silently revived.
- At most 5000 rows per file.

`catalog.import` is a separate permission from editing one product, because a
single call rewrites prices across the estate. Branch managers get
`catalog.export` only.

## Catalog (public)

No authentication. Public reads return only published, non-deleted products in
active categories that still have a sellable variant.

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/categories` | `?tree=true` for nesting; includes `productCount` |
| `GET` | `/products` | `?category=&search=&dietary=&featured=&limit=&cursor=` |
| `GET` | `/products/{slug}` | Variants, modifier groups with effective rules, combo slots |
| `GET` | `/search` | `?q=` — products and matching categories in one round trip |
| `GET` | `/branches/{id}/menu` | The storefront read model — see below |

`GET /branches/{id}/menu` is the hottest read in the system: every app launch
and every QR scan hits it. `id` accepts a branch id or its code.

- `?type=` picks the channel (`DINE_IN`, `DELIVERY`, `TAKEAWAY`, `QR`, `POS`,
  `CATERING`). Among the menus that match right now, **the more specific one
  wins** — a lunch-only menu takes over from the all-day default during its
  hours, because whoever scheduled it meant it to. `isDefault` only breaks ties
  between equally specific menus.
- `?menu={slug}` shows one menu explicitly, ignoring its schedule — that is what
  "preview this menu" means.
- `?at=` previews another moment; `?includeUnavailable=true` shows sold-out
  items marked rather than hidden, for staff screens.
- When nothing is scheduled the response is still `200`, with `menu: null` and a
  `reason` of `NO_MENU_SCHEDULED_NOW` or `NO_MENU_CONFIGURED`. A 404 would be
  wrong: the branch exists, it just is not serving that channel now.

Items come back grouped into sections, with a product's variants **collapsed
onto one card** carrying `priceFrom` and a size list — which is how a customer
thinks about it. Products added without a section appear in a trailing "More"
section rather than vanishing.

Products use **cursor pagination** for infinite scroll: pass `meta.nextCursor`
back as `?cursor=`. `nextCursor: null` means the end. Offset pagination would
skip or repeat items when the menu changes mid-scroll.

Prices are always plain **numbers**, converted from the database's decimal type
at the API boundary so no client has to special-case money.

## Dine-in surface

### Tables

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/tables` | `tables.read` — `?branchId=&area=&isActive=&search=` |
| `POST` | `/admin/tables` | `tables.create` |
| `POST` | `/admin/tables/bulk` | `tables.create` — `{ prefix, from, to, padTo?, seats?, area? }` |
| `GET` | `/admin/tables/areas` | `tables.read` — `?branchId=`, distinct areas in use |
| `GET`/`PATCH`/`DELETE` | `/admin/tables/{id}` | `tables.read` / `.update` / `.delete` |

Names are unique per branch, case-insensitively — "table 12" has to mean one
thing. `area` is free text rather than its own table: a restaurant renames
"Terrace" to "Garden" on a whim, and the value is only used for grouping.

Bulk creation lays out a dining room in one call (`{ prefix: "T-", from: 1,
to: 20 }`). Existing names are **skipped rather than failing the batch**, so
re-running after adding five more tables adds exactly those five. The range is
capped at 200 per call, because `to: 20000` is a typo that is tedious to undo.

Deleting a table is refused once it appears in order history, and otherwise
**deactivates the QR codes pointing at it**. The schema nulls `tableId` on
delete, which would otherwise leave a printed sticker quietly resolving to the
branch's default menu with no sign that the table it names is gone.

### QR codes

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/qr-codes` | `qr_codes.read` — `?branchId=&targetType=&tableId=&isActive=` |
| `POST` | `/admin/qr-codes` | `qr_codes.create` |
| `GET`/`PATCH`/`DELETE` | `/admin/qr-codes/{id}` | `qr_codes.read` / `.update` / `.delete` |
| `GET` | `/admin/qr-codes/{id}/image` | `qr_codes.print` — `?format=svg\|png&size=&markPrinted=` |
| `GET` | `/admin/qr-codes/{id}/analytics` | `qr_codes.view_analytics` — `?from=&to=` |
| `GET` | `/admin/qr-codes/analytics` | `qr_codes.view_analytics` — `?branchId=`, branch summary |

**The governing constraint is physical: a printed sticker cannot be changed.**
Once a code is on a table it may be scanned for years, so the token is opaque
and permanent and everything about where it leads lives in the row. The printed
URL is `{APP_URL}/m/{code}` and contains no menu or product id, so nothing in it
can go stale. Repointing a code — a new menu, a renamed table, a seasonal
promotion — is a `PATCH` here, never a reprint. `code` is deliberately not
editable.

Five target types:

| `targetType` | Needs | Resolves to |
| --- | --- | --- |
| `MENU` | nothing (`menuId` optional) | the pinned menu, else whatever the branch has scheduled now |
| `TABLE` | `tableId` | the table, plus a menu the same way |
| `CATEGORY` | `categoryId` | the category |
| `PRODUCT` | `productId` | the product |
| `CUSTOM_URL` | `customUrl` | an off-platform redirect |

Leaving a `MENU` code unpinned is usually right: resolution happens at scan
time against the branch's live schedule, so one sticker shows lunch at noon and
dinner at eight with no intervention.

Targets are checked against the code's branch. A code printed for Lahore cannot
be repointed at Karachi's menu — otherwise a scan in one dining room shows
another restaurant's prices. Categories and products are global, so only menus
and tables carry that check.

Custom URLs are restricted to `http(s)`. The value is printed on a sticker and
opened by a phone, so allowing arbitrary schemes would let anyone with QR edit
rights print a code that opens `javascript:` or deep-links into another app.

**The printable asset** returns the image itself, not the JSON envelope — the
URL is meant to be opened, saved and dropped into a print layout. SVG by
default, because a sticker is printed and vector stays sharp at any size. Error
correction is `M` (~15% recoverable): enough to survive a scuffed sticker
without making the code so dense it fails to scan at small sizes. The quiet zone
is fixed at 2 modules and is not caller-configurable — many scanners cannot find
a code without it. `?markPrinted=true` stamps `printedAt`, so "which codes were
never printed" stays answerable.

### The public scan

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/qr/{code}` | No auth. `?sessionId=&includeUnavailable=` |

`/m/{code}` is the printed URL; the website and the app both call this endpoint
to find out what to render. Codes are accepted in either case, since a code read
off a sticker gets typed by hand, and the alphabet excludes `I`, `L`, `O` and
`U` so `I`/`1`, `O`/`0` and `U`/`V` can never be confused.

**A stale target falls back to the menu.** A category or product a sticker points
at can be unpublished or deleted underneath it — and because products are
deleted *softly* so order history keeps its pricing context, the foreign key
never fires and the id survives. Rather than serving a product that no longer
exists, the scan returns the branch's menu with `targetUnavailable: true` and
the target nulled. Someone is standing at a table holding a phone; an error page
helps nobody, and the flag tells staff the sticker needs repointing.

An **inactive code and a missing code both return 404**. Telling a scanner that
a code exists but is switched off is information it cannot use, and it would let
someone enumerate valid codes.

Scan tracking is the one read in the system that genuinely has to write: a QR
scan *is* a `GET` — the camera opens a URL and nothing else ever happens — so
counting it anywhere else would mean counting nothing. The insert and the
counter update run in `after()`, once the response is already sent, and a failed
analytics write is logged rather than turned into a failed scan.

Every scan is stored; de-duplication happens in the analytics query, because
"how many times was this scanned" and "how many people scanned it" are both real
questions and only the raw rows answer both. `uniqueSessions` is the closer
proxy for people — one diner scanning three times while deciding is one
customer, and the anonymous `sessionId` separates that from three diners without
requiring anyone to log in.

Branch analytics also lists `neverScanned`, because "which posters is nobody
scanning" is the question worth acting on and a code with no scans never appears
in a ranking of the busiest ones.

`QrScan` is the fastest-growing table in the system by row count, so the nightly
maintenance job prunes rows older than 180 days. The headline counter lives on
`QrCode.scanCount` and never expires — only the per-day detail ages out.

## Cart

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/cart` | The caller's cart, priced against the live menu |
| `DELETE` | `/cart` | Empty it |
| `POST` | `/cart/items` | Add a line |
| `PATCH` | `/cart/items/{itemId}` | `{ quantity, notes }` — quantity `0` removes it |
| `DELETE` | `/cart/items/{itemId}` | Remove a line |
| `PUT` | `/cart/context` | `{ branchId, type }` — what every price depends on |
| `POST` | `/cart/coupon` | `{ code }` — put a code on the basket |
| `DELETE` | `/cart/coupon` | Take it off |

Works signed in **or** as a guest. A guest sends `x-session-id`: an anonymous id
the browser keeps in local storage and the app in secure storage. It is **not a
credential** — it grants nothing but a basket, which is why a cart holds no
personal data and checkout re-verifies who the buyer is.

**The cart stores intent, not prices.** A row records "one large pizza, thin
crust, extra cheese"; what that costs is resolved from the branch's live menu on
every read. So a price change, a variant going inactive or an item being 86'd
shows up in an open cart immediately — and no client can influence what it pays.

A line is fully validated *before* it is stored: the product is on this branch's
menu, the variant belongs to it, every modifier belongs to a group actually
attached to the product, and each group's min/max and required rules hold. An
invalid line must never reach the cart, or every later read has to cope with it.

An item that has since become unavailable comes back as a `problems` entry
rather than an error — someone opening a week-old cart should see "two of these
are unavailable", not an error page. Checkout is where it becomes a refusal.

**Logging in claims the guest cart.** Items are moved, not replaced, and
matching lines have their quantities added — someone who filled a basket and
then signed in to check out must not find it emptied by an older cart from
another device. The guest cart is consumed so it cannot be claimed twice.

Carts expire after 7 days and are pruned by the nightly job. That window is also
the creator-attribution window, so a cart outliving it would keep an attribution
alive past its expiry.

## Checkout

| Method | Path | Notes |
| --- | --- | --- |
| `POST` | `/checkout/quote` | Price a prospective order without placing it |
| `POST` | `/checkout` | Turn the caller's cart into an order |

`POST /checkout` requires a **verified** email — the gate that makes it safe for
an unverified account to hold a session at all. Prices are re-resolved inside
the call: whatever the client last displayed is irrelevant, the order is priced
at the moment of purchase.

**The whole write is one transaction** — the order number, the order, its lines,
its modifiers, its tax lines, its first status event, and emptying the cart. A
half-written order is not a glitch; it is a document with a legal number and no
contents, and it corrupts every report that counts orders.

Order numbers are per-branch and reset daily (`KHI1-2026-09-09-0042`), allocated
with a row lock inside that same transaction so two simultaneous checkouts get
consecutive numbers and a failure cannot burn one.

### Pricing

Every amount is computed in `src/server/pricing/engine.js`, which is pure — it
takes resolved lines plus a settings snapshot and returns numbers. Arithmetic is
`Decimal` throughout, never float.

- **Modifier deltas are per unit.** Two burgers with extra cheese is two lots of
  cheese, which is what the kitchen makes and what the customer expects to pay.
- **Tax** comes from each product's tax group. `ordering.prices_include_tax`
  decides direction: inclusive extracts the tax from the price, exclusive adds
  it on top. Compound rates stack on the running total ("tax on the tax").
  Inclusive amounts are derived by subtraction so the parts always add back to
  the gross the customer was quoted.
- **Fees** are configured, not hard-coded. `ordering.service_charge_applies_to`
  (default `["DINE_IN"]`) and `ordering.packaging_fee_applies_to` (default
  `["DELIVERY","PICKUP"]`) exist as settings because both are genuine business
  choices that differ between restaurants; burying either as an `if` in the
  pricing code makes it invisible and unchangeable.
- **Free delivery** applies above `ordering.free_delivery_above`. A threshold of
  `0` means *no* free delivery, not everything free.
- **Rounding** to `ordering.rounding_increment` records the difference on
  `Order.roundOff` so the books still balance. Defaults to `0` (off): silently
  changing what a customer is charged must be switched on deliberately.
- **Discounts** are split by what they come off. A `SUBTOTAL` discount reduces
  the taxable base — the customer is buying less value. A `DELIVERY` discount
  waives the fee and must *not* shrink the tax on the food; conflating the two
  under-charges tax on every order that used a free-delivery code. The delivery
  fee is reported gross and its waiver sits in `discountTotal`, so the discount
  rows always add back to the figure on the invoice.
- **Every discount is clamped twice** — cumulatively per row against what is
  left, then again against the order total. Two stacked 60% offers come to 100%
  split between them, never 120% with the excess quietly dropped from the total
  but still printed on the receipt.

**No endpoint anywhere accepts a price, a total or a discount from the client.**
A cart line is a product, a variant, a quantity and some choices. A mobile
binary is entirely under the user's control, so anything it claims about money
is ignored.

Staff order entry routes through the **same `placeOrder`** as customer checkout,

- **The minimum order amount does not apply.** `ordering.min_order_amount` is an

  so any order with a `placedById` is exempt.

### The status machine

Enforced server-side, per order type. Without it, a tablet in a busy kitchen
with a stale screen will happily move a delivered order back to preparing or
cancel one already in a driver's bag — and each such move corrupts reporting,
payouts and the customer's tracking screen at once.

```
DELIVERY  PENDING → CONFIRMED → PREPARING → READY → OUT_FOR_DELIVERY → DELIVERED → COMPLETED
PICKUP    PENDING → CONFIRMED → PREPARING → READY → COMPLETED
DINE_IN   PENDING → CONFIRMED → PREPARING → READY → COMPLETED
```

Any live status may go to `CANCELLED`; `PENDING` may also be `REJECTED`. An
illegal move is a **409 that names what is allowed**, so a stale client can
correct itself instead of guessing. Repeating the current status is a no-op, not
an error — a busy kitchen taps twice. Every transition writes an
`OrderStatusEvent` with who did it.

**Cancellation splits by who is asking.** A customer may call it off only while
nothing has been cooked (`PENDING`, `CONFIRMED`); after that the food exists and
someone has to decide who pays for it, so it takes staff holding `orders.cancel`.

### Tracking

`GET /orders/track/{orderNumber}` returns status, timings and the branch —
**never prices, customer details or internal notes**. A tracking link gets
forwarded, pasted into group chats and screenshotted, so it carries only what
someone waiting at the door needs.

An order number is short and guessable, so it alone is not enough: the caller
must own the order or know the phone number on it. Otherwise it is a 404.

Another customer's order is also `NOT_FOUND` rather than `FORBIDDEN` — confirming
an id exists would let someone enumerate other people's orders.

## Kitchen display

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/kds` | `kds.read` — `?branchId=&stationId=&includeReady=` |
| `GET` | `/admin/kds/summary` | `kds.read` — `?branchId=` |
| `PUT` | `/admin/kds/items/{itemId}` | `kds.update_item_status` |
| `POST` | `/admin/orders/{id}/bump` | `kds.update_item_status` |

A screen on a wall in a hot, busy room, and everything is shaped by that. The
queue is **oldest first**, because a kitchen works tickets in the order they
arrived. Each ticket carries `waitingMinutes` and `isLate` so the problem is
visible without anyone doing arithmetic. Item status changes are idempotent — a
chef with flour on their hands taps twice.

Tickets filter by station so the grill screen never shows desserts. **A product
with no station appears on every queue rather than none** — an unrouted item
that silently never gets cooked is far worse than one that appears twice.

Advancing the last outstanding line advances the order itself. Nobody in a
kitchen should have to remember to tap the ticket *and* the order, and an order
sitting in `PREPARING` with every line ready is exactly the stale state that
loses a customer's food. A combo's children follow their parent — it is one dish.

## Invoices

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/orders/{id}/invoice` | `invoices.read` |
| `POST` | `/admin/orders/{id}/invoice` | `invoices.create` |
| `POST` | `/admin/orders/{id}/invoice/void` | `invoices.void` — `{ reason }` |
| `GET` | `/admin/orders/{id}/receipt` | `invoices.read` |

Separate from the order because an invoice number is a **legal artefact**: once
issued it is never reused, renumbered or silently edited. A mistake is corrected
by voiding and issuing a new one, which is how a tax authority expects to see
it. Voiding keeps the row with `isVoid` set rather than deleting it — a number
that was issued must remain accounted for.

`/receipt` returns **data, not a PDF**. An 80mm thermal printer, an emailed A4
attachment and an on-screen receipt want the same content and disagree only
about layout. It is built entirely from the order's own snapshots — line names,
prices, modifier names and tax lines were all frozen at purchase — so a reprint
a year later shows what was actually bought, not what the catalog says today.

| `GET` | `/products/{slug}/reviews` | none — published only |
| `GET` | `/admin/reviews` | `reviews.read` — `?status=PENDING` is the queue |
| `PUT` | `/admin/reviews/{id}` | `reviews.moderate` |

**You may only review what you bought.** A review must name a delivered order of
the caller's that actually contained the product. Without that the ratings are
an open comment box, and the first bot to find it decides what the food is worth.

New reviews land `PENDING` and are invisible until moderated — publishing first
and removing later means the abuse has already been seen. Editing sends a review
back to the queue: edited text is unreviewed text.

The public endpoint returns the distribution alongside the average, because "4.2
from 500 reviews" and "4.2 from 5" are very different claims and a bare average
hides which one this is.

## Pricing, discounts & tax

### Tax administration

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/tax-groups` | `taxes.read` |

A group holds rates; a product points at a group. Rates carry a `sortOrder` and

order is a `409`; deactivate it and add a replacement. The same applies to
deleting a group still used by live products.

### Promotions

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/promotions` | `promotions.read` |
| `POST` | `/admin/promotions` | `promotions.create` |
| `GET` | `/admin/promotions/{id}` | `promotions.read` |
| `PATCH` | `/admin/promotions/{id}` | `promotions.update` |
| `DELETE` | `/admin/promotions/{id}` | `promotions.delete` |
| `PATCH` | `/admin/promotions/{id}/active` | `promotions.activate` |

Pausing is its own permission and its own endpoint: stopping an offer that is
losing money is something a duty manager needs at 8pm on a Friday, and it should
not require the ability to rewrite the offer's rules.

**Types.** `PERCENTAGE`, `FIXED_AMOUNT`, `FREE_DELIVERY`, `FREE_ITEM`,
`BUY_X_GET_Y`, `BUNDLE_PRICE`.

**Targeting.** `targets[]` scope an offer to products, variants or categories.
An empty target list means the whole order. **Exclusions beat inclusions** —
"drinks only" plus "not alcohol" reads as drinks minus the alcohol, and an
inclusion can never re-admit an excluded line.

**Eligibility** is checked before value, so a cap or a rounding bug can never
resurrect an offer that does not apply: active flag, date window, day of week,
time window, branch, channel, order type, minimum order, minimum item count,
first-order-only, and both usage caps. Empty arrays mean *everywhere* — an offer
with no branch list is chain-wide, not an offer that applies nowhere. Time
windows are minutes from midnight **in the branch's timezone**, with an end past
`1440` expressing a window that crosses midnight, exactly as menus and opening
hours do.

**Stacking**, in the order the rules bite:

1. A coupon the customer typed **always applies**. They went and found the code;
   dropping it because an automatic offer scored higher generates support
   tickets, not goodwill.
2. A non-stackable promotion is **alone** — if the coupon's promotion is
   non-stackable, nothing automatic joins it.
3. Otherwise take **the better of** the single best non-stackable offer or the
   whole stackable set. Comparing the two is what stops "20% off" and "flat 100
   off" from both being missed because each excluded the other.

A `FREE_DELIVERY` offer never competes for the single exclusive slot: it comes
off a different number.

**Deleting** a promotion that has ever been given to a customer is a `409`.
`OrderDiscount.promotionId` is how finance answers "what did this campaign cost
us"; deactivate it instead.

### Coupons

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/coupons` | `coupons.read` |
| `POST` | `/admin/coupons` | `coupons.create` |
| `GET` | `/admin/coupons/{id}` | `coupons.read` |
| `PATCH` | `/admin/coupons/{id}` | `coupons.update` |
| `DELETE` | `/admin/coupons/{id}` | `coupons.delete` |
| `GET` | `/admin/coupons/{id}/redemptions` | `coupons.read` |
| `POST` | `/admin/coupons/generate` | `coupons.generate_bulk` |
| `POST` | `/admin/coupons/revoke` | `coupons.update` |
| `POST` | `/coupons/validate` | — (public) |

A coupon is **a key, not a discount**: the promotion behind it holds every rule.
That split is what lets a campaign issue ten thousand printed codes that all
obey one rule, and lets the rule change once rather than ten thousand times.

Codes are compared case-insensitively and stored uppercase — someone typing
`save20` off a flyer reading `SAVE20` has done nothing wrong.

`/admin/coupons/generate` mints a batch under one `campaign` tag, which
`/admin/coupons/revoke` can then kill as a unit when codes leak. Collisions are
resolved by the database (`createMany` with `skipDuplicates`) and the shortfall
retried; over-generated codes are deleted so the batch is exactly what was
asked for, with no unaccounted-for live codes left behind. A code space too
small for the batch fails loudly rather than spinning.

`/coupons/validate` answers only whether the code itself is usable by this
caller — **never what it is worth**, which depends on a basket it deliberately
does not read. A code that does not exist and a code that is not yours return
the same message, so the coupon box cannot be used to enumerate other people's
personal codes. It is write-rated despite changing nothing, because it is a
yes/no oracle over a namespace of short codes.

### Manual discounts

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/orders/{id}/discounts` | `orders.read` |
| `POST` | `/admin/orders/{id}/discounts` | `orders.apply_manual_discount` |
| `DELETE` | `/admin/orders/{id}/discounts/{discountId}` | `orders.apply_manual_discount` |

Every other discount is the output of a rule written in advance. This one is a
person deciding at the counter to charge less — necessary, and the easiest way
to steal from a restaurant. So it carries controls none of the others need:

- a **separate permission**, so giving someone the till does not give them the
  ability to empty it;
- a **cap** — `pricing.max_manual_discount_percent` (default 20), deliberately
  *not* branch-overridable, because a branch that can raise its own limit does
  not have one. It is checked against the order in aggregate, so three 10%
  discounts cannot walk past a 20% limit one at a time;
- a **mandatory reason**, kept on the row rather than in a log;
- an **audit entry naming who approved it**, written synchronously — this is the
  one action where the trail matters more than the latency.

`{ amount }` **or** `{ percent }`, never both: a till that accepts "20" without
saying which eventually gives away 20% instead of 20 rupees. A paid order is
refused — that needs a refund (Phase 7), because lowering the total below what
was captured leaves money in the gateway no document accounts for. Only `MANUAL`
discounts can be removed; deleting a promotion or coupon row while its rule
still applies would make the order disagree with the offer the customer saw.

Totals are adjusted by the **delta**, never rebuilt from the parts — rebuilding
would re-decide whether tax is inclusive and re-apply the rounding increment,
two settings that may have moved since the order was placed. Tax is left alone:
the tax lines record what was charged on goods already sold, and a goodwill
discount afterwards is a commercial decision, not a restatement of that sale.

### Where discounts are resolved

The basket and the checkout resolve offers through the same code, so the cart
shows the discount the checkout will actually give. Both price **twice** — once
to get the line totals a targeted promotion must be measured against, then again
with the resulting discounts — and both passes are pure arithmetic over data
already in memory.

The two differ in one deliberate way. In the **cart**, a failure to resolve
offers is swallowed and logged: a customer who cannot see their food is a lost
order, whereas one who does not see a discount until the next refresh has merely
been under-served. At **checkout** it is not: silently dropping a code the
customer typed charges them more than they agreed to pay.

Redemption limits are enforced by the **write**, not by the check before it.
Eligibility is decided from a row read moments earlier, so two checkouts racing
for the last redemption of a limited offer would both pass it. The increment is
conditional on there still being room, so the database decides who got it and
the loser is told. Discount rows, the coupon redemption and both counters are
written in the **same transaction as the order** — a redemption without its
order burns a single-use code on nothing, and an order without its redemption
lets one code be spent forever.

## Payments

Provider-agnostic by construction. Every gateway sits behind one interface in
`src/server/payments/providers/`, and nothing outside that directory knows which
one is in use — that is what lets a chain change acquirer, or run a different
one per country, without touching the code that creates orders and issues
refunds. A provider implements `createIntent`, `capture`, `void`, `refund`,
`verifySignature` and `parseEvent`, returns plain objects, and never touches the
database; the services own persistence, so a provider can be tested with no
schema at all and a provider bug can never leave a half-written payment behind.

Two ship today: **`cash`** (counter cash, COD, standalone card terminals,
aggregator settlement — anything settled by a person rather than an API) and
**`mock`**, a fake online gateway that exercises the entire online path
end to end. Adding a real acquirer is one file plus `registerProvider`.

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/payments` | `payments.read` |
| `POST` | `/admin/payments` | `payments.capture` |
| `GET` | `/admin/payments/{id}` | `payments.read` |
| `POST` | `/admin/payments/{id}/capture` | `payments.capture` |
| `POST` | `/admin/payments/{id}/collect` | `payments.mark_collected` |
| `POST` | `/admin/payments/{id}/void` | `payments.void` |
| `GET` | `/admin/orders/{id}/payments` | `payments.read` |
| `GET` | `/me/orders/{id}/pay` | own order |
| `POST` | `/me/orders/{id}/pay` | own order |

**The client never names an amount.** A charge is "pay order X"; how much that
is comes from the order. Omitting `amount` charges the full outstanding balance;
supplying a smaller one is how a split bill works — four people paying a quarter
each is four `Payment` rows, and the order becomes `PAID` when they add up. An
amount larger than the balance is refused.

**A customer may not choose a cash-like method** on their own order. Marking
one's own order "cash received" is marking it paid for free, so `/me/orders/{id}/pay`
accepts only methods that actually move money through a gateway.

**Charging is idempotent.** Send `idempotencyKey` and a replay returns the
original payment rather than charging twice — a customer on a flaky connection
taps pay twice, and a mobile client retries a timed-out request. The same key
naming a *different* order is a `409` rather than a silent reuse, because that
is a client bug worth surfacing.

The payment row is written **before** the provider is called, so a gateway that
charges the customer and then times out still has a local record pointing at it.
The opposite order is how money gets taken for a payment the system never heard
of.

### Payment state is derived, never assigned

`Order.paymentState` summarises many payment and refund rows, so it is computed
from them after every write (`src/server/payments/state.js`) and set nowhere
else. The moment a code path assigns it from whatever it happens to be doing,
the summary and the rows disagree — and the rows are the money.

The rules that are easy to get wrong, each pinned by a unit test:

- A **refund is checked before payment**: an order paid and then refunded is
  `REFUNDED`, not `PAID`, even though the captured total still covers the bill.
- Only **completed** refunds count. One sitting in `REQUESTED`, `APPROVED` or
  `PROCESSING` has moved no money, and showing the order as refunded while the
  customer is still waiting is worse than showing it as paid.
- `FAILED` only when **every** attempt failed. A declined card next to a pending
  cash payment is an unpaid order, not a failed one — the customer still has a
  way to pay, and telling staff otherwise has them chase a live order.
- **Amount due is never negative.** An overpayment is a refund, not a credit.

### Cash on delivery and counter cash

Settled through the `cash` provider, and marked collected rather than captured —
a different endpoint on purpose, because that is the moment physical money
enters the business. It attaches the payment to an open **register session** and
writes a `SALE` movement, so it becomes part of that shift's expected cash.
Capturing without a drawer is cash nobody notices is missing.

## Refunds

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/refunds` | `refunds.read` |
| `POST` | `/admin/refunds` | `refunds.request` |
| `GET` | `/admin/refunds/{id}` | `refunds.read` |
| `POST` | `/admin/refunds/{id}/approve` | `refunds.approve` |
| `POST` | `/admin/refunds/{id}/reject` | `refunds.reject` |

```
REQUESTED ──> APPROVED ──> PROCESSING ──> COMPLETED
         └──> REJECTED                └──> FAILED
```

Money leaving the business, so the shape is governed by one question: who
decided, and can it be proved afterwards. **Requesting and approving are
separate permissions**, so the person who fields the complaint need not be the
person who authorises the money. A restaurant wanting one-step refunds grants
one role both; that is role configuration, not a code change.

Amounts are capped against what the payment actually captured minus what has
already gone back, counting refunds **still in flight** — one sitting in
`PROCESSING` has been sent to the gateway, and ignoring it would let a second
request be approved for money already on its way. The cap is re-checked at
approval, because the request may have been raised hours earlier.

The provider call sits **between** two transactions, never inside one: holding a
transaction open across a call to a slow acquirer is a table full of stuck
locks. The row moves to `PROCESSING` first, so a crash mid-call leaves a refund
that is visibly in flight rather than one that looks untouched and gets sent
twice. A provider error lands on `FAILED` and stays there — an approval that
reached the gateway may still settle, so re-approving is a decision for a human
who can check.

A cash refund writes a negative `CashMovement`, so the till still reconciles.

## Payment webhooks

| Method | Path | Permission |
| --- | --- | --- |
| `POST` | `/webhooks/payments/{provider}` | — (signature is the auth) |
| `GET` | `/admin/payment-webhooks` | `payment_webhooks.read` |
| `GET` | `/admin/payment-webhooks/{id}` | `payment_webhooks.read` |
| `POST` | `/admin/payment-webhooks/{id}/replay` | `payment_webhooks.replay` |

A webhook is an untrusted HTTP request claiming money moved, so the order is
fixed:

1. **Verify the signature over the raw body** — before parsing, before looking
   anything up, before storing. An unsigned callback is an open endpoint for
   marking any order paid. The receiver deliberately declares no body schema:
   `apiHandler`'s parsing would hand the service a re-serialised object, and
   `JSON.parse` then `JSON.stringify` does not round-trip key order or number
   formatting — a signature checked against re-encoded JSON passes when it
   should fail.
2. **Store the event**, keyed on `(provider, eventId)`, so redelivery — which
   every gateway does, often, and sometimes out of order — is a no-op.
3. **Process it**, recording the outcome on the row.

The endpoint answers `200` for anything durably stored, including events it does
not understand and events whose handler threw. A gateway receiving a non-2xx
retries with backoff and eventually disables the endpoint, so a bug in our
processing must not become a dead integration — the failure is recorded and
replayed deliberately. The one exception is a bad signature: `401`, and nothing
is stored.

Applying a capture is idempotent, and the **gateway's amount wins** over the
local one: it is what actually moved, and a mismatch is precisely what a
reconciliation must surface rather than paper over. A late "failed" event for
money already captured is recorded but not applied — that is provider ordering,
not an instruction to un-capture.

Replay does **not** re-check the signature: it was verified on arrival, and
nothing unverified is ever stored. Permission is the control instead.

## Cash registers

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/registers` | `cash_registers.read` |
| `POST` | `/admin/registers` | `cash_registers.open` |
| `GET` | `/admin/registers/{id}` | `cash_registers.read` |
| `POST` | `/admin/registers/{id}/close` | `cash_registers.close` |
| `POST` | `/admin/registers/{id}/reconcile` | `cash_registers.reconcile` |
| `POST` | `/admin/registers/{id}/movements` | `cash_registers.record_movement` |

A till session answers "was any money missing today", and only works if the
system computes the expected figure and a human types in the counted one
**without seeing it first**. So closing takes `countedCash` as input and returns
the variance, rather than displaying the expected total and asking for
confirmation — a cashier shown the answer reconciles to the answer, and the
control is worth nothing.

Everything touching the drawer becomes a signed `CashMovement`: sales and
pay-ins positive; refunds, pay-outs, drops and tip-outs negative. **The sign is
decided server-side from the movement type**, never trusted from the request, so
a pay-out sent as a positive number cannot inflate the drawer and hide a
shortfall. Expected cash is then the opening float plus the sum of movements —
derived from rows rather than a running total that can drift.

One open session per register per branch: two people taking cash into the same
named drawer makes the variance meaningless, because neither is accountable for
it. `ADJUSTMENT` is the one type with no external cause, so it must carry a
reason or it is indistinguishable from covering a shortfall. Variance is
positive for over and negative for short.

**Reconciling is a separate permission from closing**: the cashier counts, a
manager accepts. Without that split, the person who is short signs off being
short.

## Deliveries and dispatch

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/dispatch?branchId=` | `deliveries.read` + `drivers.track` |
| `GET` | `/admin/deliveries` | `deliveries.read` |
| `POST` | `/admin/deliveries` | `deliveries.assign` |
| `GET` | `/admin/deliveries/{id}` | `deliveries.read` |
| `POST` | `/admin/deliveries/{id}/assign` | `deliveries.assign` / `reassign` |
| `POST` | `/admin/deliveries/{id}/unassign` | `deliveries.reassign` |
| `PUT` | `/admin/deliveries/{id}/status` | `deliveries.update_status` |
| `POST` | `/admin/deliveries/{id}/handover-code` | `deliveries.update_status` |
| `GET` | `/admin/deliveries/{id}/track` | `drivers.track` |
| `GET` | `/orders/track/{orderNumber}/delivery` | — (public) |

The delivery row is created when the order is **ready to leave**, not when it is
placed — a job that exists before there is anything to carry clutters every
dispatch board with work nobody can do. It is created automatically when a
delivery order reaches `READY`, routed through the outbox so the dependency
between the order and delivery services points one way. Creation is idempotent;
`Delivery.orderId` is unique and dispatch screens retry.

```
PENDING → ASSIGNED → ACCEPTED → ARRIVED_AT_STORE → PICKED_UP
        → ON_THE_WAY → ARRIVED → DELIVERED
```

Everything **before pickup** can return to `PENDING` — an unaccepted or rejected
job simply goes back to the pool. **Nothing after** can: the food is in
someone's bag, and pretending otherwise loses track of it. Reassigning a
delivery whose driver is already carrying it is a `409`; that case is a failure
to record, not a reassignment. A failed drop can be sent out again; a delivered
one cannot.

The driver app shares one entry point with dispatch, narrowed by `byDriver`: a
driver may move their own job forward, reject it and report a failure, but
cannot cancel an order, hand work back after pickup, or touch a job that is not
theirs — which answers `404` rather than `403`, so the endpoint cannot be used
to discover delivery ids. Failing a delivery requires a reason, and is a
separate permission from updating status.

`maxActiveOrders` is **per driver** rather than a global setting, because it is
genuinely personal: a cyclist with an insulated bag carries fewer orders than a
van. Pickup and delivery are mirrored onto the order (`OUT_FOR_DELIVERY`,
`DELIVERED`) so a customer is never watching "preparing" while the driver is at
their door; intermediate steps are detail the order does not need.

### Handover and proof

`delivery.require_handover_code` and `delivery.require_proof_photo` are
per-branch, because they are a real operational trade-off: a code stops
"delivered" being tapped from the end of the street, and it also strands a
driver whose customer is not answering their phone.

The code is four digits, **stored only as a hash** — exactly like a password. A
code sitting in plain text is one any staff member can read off a screen and
pass to a driver who never went to the door. It is returned once, at issue, and
cleared on delivery so a photographed code cannot be replayed.

### COD is the driver's debt

Collecting cash at the door captures the `CASH_ON_DELIVERY` payment **and**
increases `Driver.cashInHand`, in one transaction. Both halves matter: the order
is settled, and somebody is on the hook for the notes in their pocket. The
amount is capped at what the order actually owes. That balance is settled at
shift end and deducted from the payout if it is not — so a driver cannot simply
keep it.

### Tracking

`POST /me/driver/location` is the one endpoint meant to be called continuously,
so it is deliberately **not** write-rate-limited. The last known point is
overwritten on `Driver` — enough for a dispatch board to draw something before
the first realtime frame — while breadcrumbs are written to the active delivery
only every ~30 seconds. A row per ping would be millions a day per city for data
nobody reads outside a dispute, and they are pruned on a retention schedule by
the maintenance job.

The public tracking endpoint is narrow on purpose. A tracking link travels
through messaging apps authenticated by nothing but the order number, so it
returns the driver's **first name**, vehicle and rating — never a phone number —
and the position **only while they are carrying that order**, not before and not
once they have moved on to someone else's.

A payout is a **snapshot**, not a live query: once generated its lines say what

one figure on Monday and paid another on Friday with nothing explaining why.

Only **delivered** jobs count — paying for a failed drop would make cancelling
attractive. Each is counted exactly once by construction:
`DriverPayoutLine.deliveryId` is how a drop is marked as counted, so overlapping
periods cannot pay for the same work twice. Cancelling a payout deletes its
lines, so the deliveries it covered become countable again rather than being
stranded unpaid forever.

COD is where the two flows meet: earnings owed **to** the driver, less cash owed
**by** them. Marking a payout paid clears that debt — decremented rather than
zeroed, because the driver may have taken more COD since the payout was
generated and that money is still owed.

## Inventory

The distinction the whole module rests on: a **`Product`** is what a customer
buys; an **`InventoryItem`** is what it is made of. One burger consumes a bun, a
patty and 30g of cheese, none of which are products, and the cheese is used by
nine other dishes. Collapsing the two is the modelling mistake that leaves a
restaurant system unable to say what anything costs.

### The ledger is the truth

**Every** stock change goes through `postMovement` — not most of them, every
one. `StockMovement` is append-only and authoritative; `StockLevel` is a cache
that exists only because summing a million rows on every screen is too slow. The
moment another code path updates a level directly, the cache and the truth
disagree, and the only way to find out is a stock count that comes up short with
nothing to explain it.

That single path is what makes `POST /admin/stock/rebuild` possible: replay the
ledger and every level is provably correct again. It reports what it corrected —
a non-empty `drift` means something wrote around `postMovement`, which is a bug
to chase rather than a number to fix quietly.

**Direction comes from the movement type, never the caller's sign.** A wastage
sent as a positive number still removes stock. `COUNT_CORRECTION` and
`OPENING_BALANCE` are the two exceptions, where the sign *is* the finding.

`allowNegative` is a deliberate per-call decision rather than a global rule: a
sale that already happened must be recorded even when the system thought the
shelf was empty, while a transfer off an empty shelf should be refused.

### Units

| Method | Path | Permission |
| --- | --- | --- |
| `GET` `POST` | `/admin/units` | `units.read` / `units.manage` |
| `GET` `PATCH` `DELETE` | `/admin/units/{id}` | `units.read` / `units.manage` |

A unit either *is* a base or converts to one of the same type, one hop only —
g → kg → tonne would make the factor depend on how far you walk, and one bad
link corrupts everything downstream. Converting across types is **refused**, not
guessed: treating "2 L" as "2 kg" silently is worse than rejecting the line.

Once a unit has been used its conversion is immutable, because past movements
stored quantities already converted through the old factor.

A **unit cost converts the opposite way to a quantity** — 500 per kg is 0.5 per
gram, not 500,000 — which is why that is a separate function rather than a
second call to the quantity converter.

### Batches and expiry

| Method | Path | Permission |
| --- | --- | --- |
| `GET` | `/admin/stock-batches` | `stock_batches.read` |
| `GET` | `/admin/stock-batches/expiring` | `stock_batches.read` |
| `PUT` | `/admin/stock-batches/{id}/status` | `stock_batches.quarantine` |
| `POST` | `/admin/stock-batches/{id}/write-off` | `stock_batches.write_off` |

FIFO consumes by **soonest expiry, then oldest receipt**. Expiry first on
purpose: stock spoiling next week has to leave before stock received a day
earlier that lasts a month, or the older batch is used and the newer one is
thrown away.

**Quarantine is not a write-off.** A suspect delivery may turn out to be fine, so
the stock stays on the books and in the valuation but stops being allocated —
FIFO only considers `ACTIVE` batches. A write-off posts a `WASTAGE` movement
rather than editing the batch, so the loss reaches the ledger, the wastage report
and the cost of goods; stock that vanishes from the numbers is stock nobody
learns from.

The nightly job flags passed-expiry batches as `EXPIRED` but deliberately does
**not** write them off — expired stock physically exists and has to be counted
and disposed of by a person, and silently removing it would destroy the evidence
of how much is being wasted.

**A purchase order moves no stock.** Ordering food is not the same as having it,
and a system that increments stock on order is one that thinks a late delivery is
already in the fridge. Lines price from the supplier's agreed list when no price
is given, and **no request ever states a document total** — subtotal, tax and
grand total are all derived.

Editing is allowed only in `DRAFT` and `PENDING_APPROVAL`; after approval the
document is what someone signed off. Cancelling is refused once anything has been
received — the goods exist and the supplier is owed for them, so the honest end
is a short **close**, not a cancellation pretending the delivery never happened.

### Goods receipts

The most consequential write in the module, so three things hold by construction:

- **Posting is one transaction** — the GRN, its lines, the batches, the stock
  movements and the order's received quantities either all exist or none do.
- **Rejected quantity never enters stock.** What was delivered and what was
  accepted are different numbers, and the difference is why deliveries are
  inspected.
- **Landed cost is spread before the batch is priced.** Freight is allocated
  across lines *by value* — a pallet of napkins and a box of saffron do not
  attract the same share of a freight bill — and any rounding remainder goes on
  the largest line so the parts add back to the whole. Get this wrong and every
  margin looks better than it is.

Posting is idempotent at the document level: a completed receipt is returned
unchanged rather than posted twice, because a double-posted delivery is stock
that never arrived. Over-receipt against an order is refused, compared in the
*order's* unit so a sack-vs-kg mismatch cannot make it look acceptable.

**Transfers are two steps because of stock in transit.** A van carrying meat has
left one place and not arrived at the other; a single-step transfer would make it
appear instantly at the destination and any shortfall on arrival would be
invisible. Receiving less than was sent writes the difference off at the
**source** as wastage — someone dispatched it, and the loss belongs to that
journey. The cost travels with the goods, so moving stock never invents or
destroys value.

**Counts freeze the system quantity when the sheet is opened**, not when it is
posted: comparing against a live figure means comparing against a number that
moved while the counting was happening. `GET /admin/stock-counts/{id}?blind=true`
hides the expected quantity — the same reasoning as a blind cash count, since
someone who can see the expected number will find it. Posting is separate from
counting and separately permissioned: the person who is short should not be the
person who accepts being short.

**Adjustments are approval-gated; wastage posts immediately.** An adjustment with
no justification is indistinguishable from theft being written off, so it waits
for approval. Waste has already happened — the food is in the bin — and holding
it on the books until a manager gets round to approving would make every
intervening count wrong; approval there reviews the loss rather than gating the
ledger. Wastage is kept separate from a negative adjustment because **it is a
number a kitchen is managed on**: burying spoiled food inside "adjustments"
destroys the only signal that a fridge is failing.

## Sale-time depletion

The join between the catalog and the store room, and what makes
theoretical-versus-actual usage possible — the single most valuable number in
restaurant inventory. Without it, stock only changes when somebody remembers to
type something in.

A completed order's lines are exploded through each variant's recipe, recursively
for sub-recipes, plus any modifier carrying ingredients ("extra cheese" is 30g of
cheese). Each ingredient is converted into the item's stocking unit and grossed
up for prep yield.

Two decisions shape it:

- **Depletion never blocks a sale.** It runs from the outbox after the order
  completes, and posts with `allowNegative`. The food has physically left the
  kitchen; refusing to record that because the shelf looked empty would make the
  ledger *more* wrong, not less.
- **It is idempotent per order.** Movements are tagged with the order id and an
  already-deducted order is skipped, so a redelivered event cannot empty a store
  room twice.

Cancelling an order that was already deducted posts a `CUSTOMER_RETURN` rather
than deleting the original movements — the ledger is append-only, and a sale that
happened and was reversed is two facts, not zero.

`GET /admin/stock/usage-variance` compares what the recipes say should have been
used against what the ledger says left the shelf. A persistent gap is portioning
drift, unrecorded waste, or theft — invisible without the comparison.

## Recipes and costing

`/admin/recipes` — the bill of materials for everything the kitchen makes.

A recipe produces **exactly one** thing, and which one decides how stock behaves
around it:

| Output | Endpoint field | What happens to stock |
| --- | --- | --- |
| Sellable dish | `variantId` | Nothing is made in advance; the recipe is exploded at sale time and raw stock is deducted then |
| Inventory item | `outputItemId` | Made by a production run, becomes stock in its own right, and can then be an ingredient in other recipes |

An ingredient line is either an `itemId` or a `subRecipeId`, never both. Units
are validated on the way in: a line in litres against an item stocked by weight
is refused at save time, where a chef can fix it, rather than at midnight when a
sale tries to deduct it. Sub-recipe lines are measured in the sub-recipe's own
yield unit — "150 ml of sauce" against a sauce recipe yielding 2 litres explodes
as 0.15, not 150.

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/admin/recipes` | Costs withheld without `recipes.view_cost` |
| POST | `/admin/recipes` | `recipes.create` |
| GET | `/admin/recipes/{id}` | Includes `usage`: production runs and parent recipes |
| PATCH | `/admin/recipes/{id}` | In place — refused once produced against |
| DELETE | `/admin/recipes/{id}` | Refused if used anywhere; deactivate instead |
| POST | `/admin/recipes/{id}/revise` | Creates the next version |
| POST | `/admin/recipes/{id}/activate` | Makes one version live — the rollback |
| GET | `/admin/recipes/versions` | Every version of one output, newest first |
| GET | `/admin/recipes/{id}/cost` | The full cost tree. `recipes.view_cost` |
| POST | `/admin/recipes/{id}/recost` | Rolls up and caches |
| POST | `/admin/recipes/recost` | Every active recipe |
| GET | `/admin/recipes/menu-cost` | Cost against price, worst food-cost first |

**Versions are immutable once used.** A recipe that has been produced against is
the record of what was made and what it cost; editing it in place would silently
rewrite history and move every past variance. Such an edit is refused with a 409
pointing at `/revise`, which creates version n+1 and deactivates the old one
without deleting it. Exactly one version of an output is live at a time.

Cycles are refused at save time. "Dough" using "starter" using "dough" is a
plausible mistake in a bakery, and it makes both costing and depletion recurse
until something dies.

### What a roll-up includes

Ingredients at the item's current cost, plus the recipe's own labour and
overhead, divided by the yield — so the answer is the cost of **one portion**,
comparable with a menu price without anybody dividing by hand. Sub-recipes are
costed recursively rather than read from their cached figure; the cached
`computedUnitCost` is a result of a roll-up, never an input to one.

`missingCosts` lists every ingredient with no cost on it, and the gap propagates
upwards through sub-recipes. An item that has never been received has an average
cost of zero, and a recipe full of them rolls up to nothing at all — which reads
as a wonderfully profitable dish rather than as missing data. `isFullyCosted`
says which it is.

`POST /admin/recipes/{id}/recost` also refreshes the variant's `standardCost`.
That is the number an order line snapshots as COGS at sale time, so a stale one
misstates the margin on every sale until the next roll-up.

`GET /admin/recipes/menu-cost` returns `foodCostPercent: null` for an uncosted
dish rather than zero — unknown is not the same as free, and reporting it as 0%
would put it at the top of the most-profitable list.

## Production

`/admin/production-orders` — the prep kitchen. A run turns raw stock into
something else: flour and water into dough, bones into stock, a whole lamb into
portions.

```
PLANNED ──▶ IN_PROGRESS ──▶ COMPLETED
   │             │
   └─────────────┴────────▶ CANCELLED
```

| Method | Path | Permission |
| --- | --- | --- |
| GET | `/admin/production-orders` | `production_orders.read` |
| POST | `/admin/production-orders` | `production_orders.create` |
| GET | `/admin/production-orders/{id}` | Planned against actual usage, line by line |
| PATCH | `/admin/production-orders/{id}` | Only while planned |
| GET | `/admin/production-orders/{id}/plan` | The pick list, in stocking units |
| POST | `/admin/production-orders/{id}/start` | `production_orders.start` |
| POST | `/admin/production-orders/{id}/consume` | Extra material mid-run |
| POST | `/admin/production-orders/{id}/complete` | `production_orders.complete` |
| POST | `/admin/production-orders/{id}/cancel` | `production_orders.cancel` |
| GET | `/admin/production-orders/variance` | Actual against standard, by run and recipe |

Only a recipe that makes an **inventory item** can be produced. A burger is not
something the store room holds, so a variant recipe is refused here and depleted
at sale time instead.

Four rules:

- **Material is issued at start, not at completion.** That is what happens in a
  kitchen, and it means stock is not overstated for the hours a batch is
  proving. It also gives a cancelled run something real to put back.
- **Starting is refused if the material is not there.** Unlike a sale — already
  a fact by the time the system hears about it — a run is a decision being taken
  now, and issuing flour that does not exist leaves a negative balance nobody
  can explain later.
- **Output is costed at what the run actually cost**: the FIFO or average cost
  of what was consumed, plus labour and overhead. Not the recipe's estimate —
  that is the *standard*, frozen at start, and the gap between the two is the
  point of the whole module.
- **Waste is booked, not absorbed.** `wastedQuantity` is yield loss: made, but
  not usable. It is booked into stock and immediately written off against the
  run as a costed `PRODUCTION_LOSS` wastage record, so the loss is a number
  somebody can be asked about instead of a silent uplift in the cost of what
  survived.

Omitting `items` on `/start` issues exactly what the recipe calls for. Passing
them records what really went in, which is what makes a usage variance possible
at all.

By-products — trimmings, stock made from bones — are credited at their own
standard cost and the primary output absorbs the rest. Nobody runs a stock pot
in order to make bones, so the bones must not carry away part of the cost of the
roast.

Cancelling an in-progress run reverses every consumption at the cost it left at,
back onto its own batch where one was recorded. Reversed rather than deleted:
material issued and returned is two facts, not none.

A variance is always **actual − standard**, and `favourable` is returned
explicitly — a positive cost variance is bad while a positive yield variance is
good, and mixing the two up inverts a report.

## Journal

Everything reaching the general ledger goes through one posting path. That is
what makes three claims true at once:

- **Every entry balances.** Postgres cannot express "debits equal credits" — it
  is a constraint across rows — so it is enforced on the way in and re-checked
  by `GET /admin/journal-entries/audit`.
- **A posted entry is immutable.** No update, no delete. A correction is a
  reversing entry pointing back at the original, so the mistake and the fix are
  both visible.
- **Nothing lands in a closed period.** The guard runs inside the posting
  transaction, so a period closing concurrently cannot be posted into through a
  gap between the check and the write.

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/admin/journal-entries` | Filter by source, status, period, account, date |
| POST | `/admin/journal-entries` | Draft unless `post: true` |
| GET | `/admin/journal-entries/{id}` | |
| POST | `/admin/journal-entries/{id}/post` | Period checked now, not at draft time |
| POST | `/admin/journal-entries/{id}/reverse` | The only correction for a posted entry |
| POST | `/admin/journal-entries/{id}/void` | Drafts only |
| GET | `/admin/journal-entries/audit` | Re-checks that the ledger adds up |

A line is a debit **or** a credit, never both, and never negative — a negative
credit is a debit, and allowing both spellings breaks any report that sums a
column. An unbalanced entry is refused with the actual difference in the
message.

Creating and posting are separate permissions so a manual entry can be reviewed:
it is the one posting no business event justifies.

## Posting rules

Business events become journal entries **out of band, from the outbox**. The
sale has happened, the stock has moved, the driver has been paid — refusing to
record an operational fact because an account was missing would make the system
less true, not more. So a posting failure is retried, never propagated backwards,
and every rule is idempotent on its source.

| Event | Entry |
| --- | --- |
| Order completed | Dr Receivable, Dr Discounts · Cr Sales, Delivery, Service, Tips payable, Tax |
| Order cost | Dr COGS · Cr Inventory |
| Payment captured | Dr Cash/Bank/Clearing, Dr Gateway fees · Cr Receivable |
| Refund completed | Dr Sales, Dr Tax payable · Cr wherever it was paid from |
| Goods receipt posted | Dr Inventory at landed cost · Cr Goods received not invoiced |
| Supplier bill approved | Dr GRNI, Dr Tax payable · Cr Accounts payable |
| Bill paid | Dr Accounts payable · Cr Bank/Cash |
| Production completed | Dr Inventory, Dr Wastage · Cr Inventory, Labour, Overhead |
| Wastage recorded | Dr Wastage · Cr Inventory |
| Stock adjusted | Dr/Cr Inventory · Cr/Dr Inventory variance |
| Driver payout approved | Dr Delivery expense · Cr Cash (COD kept), Cr Driver payable |
| Till closed | Dr/Cr Cash · Cr/Dr Cash over and short |
| Expense approved | Dr expense account, Dr Tax payable · Cr paid-from account |

Four of these are worth spelling out:

- **A sale debits receivable, not cash — even for a cash order.** The sale is
  earned when the food is handed over; the money arriving is a separate event,
  and for an unpaid order it may never happen. Posting straight to cash means an
  order completed today and paid tomorrow shows as income with no money behind
  it, and tomorrow's payment double-counts.
- **Tax-inclusive pricing is derived from the order's own figures**, not read
  from `ordering.prices_include_tax`. That setting is mutable: flipping it would
  silently re-post historical orders, moving revenue between sales and tax
  payable for transactions that closed long ago.
- **A goods receipt credits GRNI, not payables.** The delivery and the invoice
  arrive days apart. Crediting payables on arrival makes every unbilled delivery
  look like an approved invoice, and the two double up when the real one lands.
- **Production credits labour and overhead**, it does not debit them. They were
  charged to their own accounts when the wages were run and the bill was paid;
  production absorbs them into the value of the stock it creates.

| GET | `/admin/reports/cash-flow` | `financial_reports.view_cash_flow` |
| GET | `/admin/reports/summary` | The close pack, with its own tie-out checks |

Drawn from **posted** entries only — a draft is somebody's unfinished work, and
including it would make a report change under the reader as a colleague typed.

The P&L is a period statement, so `from` matters: without it you silently report
since the beginning of time. The balance sheet is cumulative and takes `asOf`
with no `from` at all; passing a range would produce a statement of movements
dressed up as a statement of position, and it would not balance.

`balanceSheet.currentEarnings` is the profit for the year so far, carried into
equity. Without it a mid-year balance sheet is out by exactly that amount — the
commonest way a home-grown ledger produces a visibly wrong report. Both the
trial balance and the balance sheet return `balanced`, so a caller never has to
add the columns up to find out.

late to the person waiting for it.

## Shifts and roster

Shift times are **minutes from midnight**, and a night shift's `endMinute` runs
past 1440 — 22:00–06:00 is 1320 to 1800. Storing the end as 360 would make every
duration negative and every night worker appear to have worked minus sixteen
hours. An end at or before the start is rolled forward a day automatically.

| Method | Path | Permission |
| --- | --- | --- |
| GET/POST | `/admin/shifts` | `shifts.read` / `shifts.manage` |
| GET/PATCH | `/admin/shifts/{id}` | Retiming a worked shift is refused |
| GET | `/admin/roster` | `rosters.read` |
| POST | `/admin/roster` | `rosters.manage` — upserts per day across a range |
| DELETE | `/admin/roster/assignment` | Refused once the day is derived |

A **weekly off is a roster row**, not the absence of one. A day nobody rostered
is unknown; a day rostered as off is one the employee was not expected on and
must not be marked absent for.

## Punches

`POST /devices/punches` takes `x-device-key` and a batch. It returns counts
rather than failing the batch, because a terminal that gets an error for 200
punches over one malformed row retries the whole batch for ever.

```json
{ "accepted": 6, "duplicates": 0, "unmatched": 1, "rejected": 0, "cursor": "6" }
```

- **De-duplicated on `(deviceId, deviceLogId)`.** Terminals replay their buffer
  after any network wobble; without the unique key a re-sync doubles everybody's
  hours.
- **An unknown biometric id is kept, not dropped.** Enrolment lags hiring, and
  discarding those punches loses attendance nobody can recover. They appear in
  `/admin/attendance-punches/unmatched`, grouped by the id the device sent, and
  `/admin/attendance-punches/claim` links them and enrols the id.
- **A punch dated in the future is refused** — a terminal with a wrong clock
  would otherwise land punches in a period that has already been paid.

`POST /admin/attendance-punches/manual` is the correction path. Punches are
never edited: a manual punch is added alongside and the day is re-derived.

## Attendance

`AttendanceDay` is a **derived cache** in the way `StockLevel` is — the punches
are the truth, and re-deriving over the same punches gives the same day, so a
nightly run and a re-sync are both safe.

| Method | Path | Permission |
| --- | --- | --- |
| GET | `/admin/attendance` | `attendance.read` |
| POST | `/admin/attendance/derive` | `attendance.edit` — idempotent |
| PATCH | `/admin/attendance/{id}/correct` | Requires a reason |
| POST | `/admin/attendance/{id}/revert` | Drops the override |
| POST | `/admin/attendance/approve` | `attendance.approve` |
| GET | `/admin/attendance/summary` | The month as payroll reads it |

| Status | Pays | When |
| --- | --- | --- |
| `PRESENT` / `LATE` | 1 | Full day worked |
| `HALF_DAY` | 0.5 | Past the half-day threshold |
| `ON_LEAVE` | 1, or 0 unpaid | Approved leave covers the day |
| `HOLIDAY` / `WEEKLY_OFF` | 1 | Calendar, and nobody punched |
| `MISSING_PUNCH` | **0** | Punched in, never out |
| `ABSENT` | 0 | Rostered, no punches |

**A missing punch-out is flagged, never guessed.** Assuming somebody left at
their shift end pays unworked hours; assuming they never arrived steals worked
ones. Paying nothing until a human looks is the safe direction — an
under-payment gets reported by the person affected, an over-payment does not.

A **correction survives re-derivation**. One that evaporates on the next nightly
run is worse than none, because whoever made it believes it stuck. `force: true`
on derive is the deliberate way to overwrite one.

A 2am punch resolves to the **previous** day's night shift. Grouping punches by
calendar date alone splits every night worker's shift across two days, halving
one and inventing the other.

## Leave and holidays

| Method | Path | Permission |
| --- | --- | --- |
| GET/POST | `/admin/leave-types` | `leave_types.read` / `.manage` |
| GET/POST | `/admin/leave-requests` | `leave_requests.read` / `.create` |

The balance is consumed **on approval, not on request**. Holding it against

asking for anything else, and a rejection has to give the days back — one more
path to get wrong. Overlapping requests are refused outright: two approved
leaves over one day each consume a day while the employee is absent once.

Approving leave **re-derives the days it covers**, so a day already marked
`ABSENT` becomes `ON_LEAVE`. Without that the employee is docked for leave
somebody granted them. `annualQuota: 0` means unlimited. A holiday with no
`branchId` is company-wide.

## Payroll

| Method | Path | Permission |
| --- | --- | --- |
| GET/POST | `/admin/payroll-periods` | `payroll.read` / `payroll.process` |
| GET | `/admin/payroll-periods/{id}` | |
| POST | `/admin/payroll-periods/{id}/generate` | `payroll.process` |
| POST | `/admin/payroll-periods/{id}/approve` | `payroll.approve` |
| POST | `/admin/payroll-periods/{id}/mark-paid` | `payroll.mark_paid` |
| POST | `/admin/payroll-periods/{id}/cancel` | Refused once paid |
| GET | `/admin/payslips` | `payslips.view_all` |
| GET | `/me/payslips` | **Your own** — no permission needed |

**Payroll reads `AttendanceDay`, never punches.** The day is the row a
supervisor corrected and approved; paying from raw punches would pay what the
terminal recorded and silently discard every correction.

A monthly salary is **prorated over the period's own days**, not a fixed 30.
February and July pay the same monthly figure, so a day off must cost the same
fraction in both. Percentage components are computed on the **prorated** base —
otherwise somebody absent half the month keeps a full month's allowance. A
salaried employee still earns overtime, at a rate derived from their salary;
returning zero means a manager covering two double shifts is paid for neither.

Payslip lines carry `quantity` and `rate` as well as the amount, so a payslip
shows its working. "Basic 12,000" invites a dispute; "22 days at 545.45" answers
one. Net is floored at zero — deductions larger than the pay are a data problem,
and a negative wage is not a thing that can happen.

Generation is **re-runnable while the period is a draft**, so a corrected
attendance day flows straight through; approved and paid payslips are left
alone. **Approval** locks the attendance it paid and posts the wage bill:

```
Dr Salaries and wages   gross
  Cr Salaries payable   net
  Cr Tax payable        withheld
```

Gross, not net: the deductions are money withheld from a wage fully earned, and
posting net understates the cost of employing people by exactly the amount
deducted. Marking paid posts the second entry, clearing the payable.

`GET /me/payslips` is deliberately a separate endpoint rather than the admin one
with a filter. Reading anybody's payslip needs `payslips.view_all`; reading your
own needs nothing but being you, and conflating the two is how one endpoint
leaks the whole payroll. It returns approved and paid slips only.

**Postings need the fiscal calendar.** Nothing posts into a date that is not in
an accounting period, so a system with no `FiscalYear` accumulates business
events that never reach the books — and the backfill cannot help until the year
exists. Create it before going live.

## Creator program

Customers film the food they bought, the team approves it, the video goes live
on that product, and sales it drives earn **store credit**. The money never
leaves as cash.

### Joining

| Method | Path | Notes |
| --- | --- | --- |

Eligibility is **proved, not claimed**: at least one COMPLETED order, and the

"you'll be able to join once this order is complete" is a very different message
from "you're not eligible". Terms acceptance is pinned to the version the
creator actually saw, and is written in the same transaction as the profile — a
profile without an acceptance is not a state worth being able to reach.

see what was rejected.

The attempt limit counts **rejections**, not uploads — a creator whose first
four attempts were approved has used nothing up. Hitting it locks the line
permanently.

are recomputed from live strikes rather than incremented, so revoking a strike
genuinely lifts the suspension it caused. A takedown leaves existing
attributions alone by default — a video pulled for poor quality did not un-sell
food somebody already bought; `revokeAttributions: true` is the explicit choice
for fraud.

Ordered featured-first then newest, deliberately **not** by views: a feed ranked

### Attribution

**Created only on add-to-cart from a video**, by passing `creatorVideoId` to
`POST /cart/items`. One row per (cart, product); the last video to put that
product in the basket wins, and every touch is kept as the audit trail.

At checkout the live rows are **frozen onto the order** before the cart is
emptied — the cart is about to disappear, and with it the creator's claim.
Amounts come from the order lines, because the viewer is free to change quantity
or variant between watching and paying. Watching one variant and buying another
still counts: somebody sold them a pizza.

Attributions survive a guest cart being merged at sign-in. They also expire with
their window, which is measured from the touch rather than the order.

### Commission rules

| Method | Path | Permission |
| --- | --- | --- |
| GET/POST | `/admin/creator-commission-rules` | `.read` / `.create` |
| GET/PATCH/DELETE | `/admin/creator-commission-rules/{id}` | Delete refused once it has paid |
| POST | `/admin/creator-commission-rules/simulate` | `.read` |

**Exactly one rule applies per attributed line.** Rules are never stacked — two
overlapping campaigns paying together produce a promotion nobody modelled and an
unbounded payout. Resolution: highest `priority`, then specificity (creator >
product > category > global), then most recently created.

`conditionBasis` and `basis` are separate on purpose: "5% of the line, on orders
over 2000" is a line-level reward with an order-level gate.

The **simulator** answers "what would this pay, and which rule wins" and returns
every candidate with whether it qualified. The alternative is discovering the
interaction between four overlapping campaigns by underpaying somebody.

### Earnings and the wallet

| Method | Path | Permission |
| --- | --- | --- |
| GET | `/admin/creator-earnings` · `/summary` | `creator_earnings.read` |
| POST | `/admin/creator-earnings/{id}/reverse` · `/reject` | `.reverse` |
| DELETE | `/admin/creator-attributions/{id}` | Refused once credited |
| GET | `/admin/creators/{id}/wallet` | `creator_wallets.read` |
| POST | `/admin/creators/{id}/wallet/adjust` | `.adjust` |
| PUT | `/admin/creators/{id}/wallet/freeze` | `.freeze` |
| GET | `/me/creator/wallet` · `/redeemable` · `/earnings` | Own only |
| POST | `/api/internal/jobs/creator-credit` | Credits earnings past their hold |
| POST | `/api/internal/jobs/creator-rollup` | Folds yesterday's engagement |

An earning is written for **every** attributed line on a completed order,
including the ones that earn nothing — `NOT_QUALIFIED`, with the reason, so a
creator sees "your video drove this sale but it missed the threshold" rather
than silence. Everything is snapshotted, and the engine is idempotent per
`(order, video)`.

Earnings sit `PENDING` through the refund hold, mirrored in the wallet's
`pendingBalance` and deliberately **not** spendable. The crediting job moves
them across.

The wallet is an append-only ledger with a cached balance and a
`rebuildBalances` replay. Redemption is limited by the smallest of the balance,
the program minimum and the per-order percentage cap — the cap is what keeps
credit a top-up rather than a way to make every order free.

A refund reverses the earning and returns any credit the customer spent. A
credited earning is debited back out, possibly into the negative: the credit was
spent on food that was then refunded, and pretending otherwise leaves the
program short.

## CORS

React Native's native runtime ignores CORS, so nothing is needed for the app
itself. Expo **web** builds and any separately-hosted front end do need their
origin allowlisted:

```bash
CORS_ALLOWED_ORIGINS="https://app.foodzone.com,http://localhost:8081"
```

Credentials are permitted, so origins are echoed individually — a wildcard is
never sent.

## Minimal React Native client

```js
const BASE = "https://your-domain.com/api/v1";

async function apiFetch(path, { method = "GET", body, token } = {}) {
  const res = await fetch(`${BASE}${path}`, {
    method,
    headers: {
      ...(body ? { "Content-Type": "application/json" } : {}),
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
    body: body ? JSON.stringify(body) : undefined,
  });

  const payload = await res.json();
  if (!payload.success) {
    const err = new Error(payload.error.message);
    err.code = payload.error.code;      // branch on this
    err.details = payload.error.details;
    throw err;
  }
  return payload.data;
}
```

On `UNAUTHORIZED`: call `/auth/refresh` with the stored refresh token, save the
**new** pair, and replay the original request once. If the refresh also fails,
send the user to the login screen.

## Adding endpoints

Business logic belongs in `src/server/services/` — never in a route handler or a
React Server Component — so the website and the app cannot drift apart. Route
handlers should only validate input, call a service, and return `ok(...)`.
